\section{General Information}

\subsection{Summary}

The software focused on in this document is the Physiotherapy Companion application, built for smart devices with camera access to help guide a patient undergoing physiotherapy with their assigned physiotherapy exercises.

The application will provide support and guidance for the exercise and provide real-time feedback to help the user using a video-feed. It will also provide overviews of previous exercises to allow users to see progress and consistency, assisting in forming healthy habits towards recovery and reinforce confidence.

The application will also support a more administrative function for physiotherapists, allowing them to view exercise summaries for patients assigned to them. Additionally, physiotherapists may leave comments on summaries to ensure consistent and timely usage of the application for healthy exercising.


\subsection{Objectives}

The objectives of the testing expanded upon within this document focus on general system usability, the security of user profiles and video-feed data, and the verification of stakeholder requirements.

Usage of the system should be easily explainable for first-time users with simple dialogue popups and limited visible guiding from one function to the next. Additionally, for the video-feed portion of the application’s usage, the user should be reasonably guided through the exercise and process to set them up for successful exercise execution and feedback recommendation acceptance.

User profile and video-feed data should be securely stored, whether locally or within a remote database accessed by the system. User data security has become an increasingly sensitive topic within the software industry of late and users may question how their data is being stored and utilized. Users should be aware of the usage of their data and the system should ensure unauthorized access outside of the communicated plan is never possible.

Meeting stakeholder requirements, whether they be data restrictive or process flow in nature, is what will validate the core features of the system. If users do not find value in the expected usage expected from the system, then, ultimately, the system has failed to perform its primary goal. Ensuring stakeholder requirements and feedback are incorporated into the system as it is developed, both initially and onward, will ensure the system is both wanted and usable to the intended audience.

Some out-of-scope objectives include performance and user-interface quality. In this sense, quality means the overall refinement and how polished the interface looks. The implementation should not inhibit usability, but the design need not be too meticulous and visually pleasing.

For performance, the system should respond in a timely manner that does not frustrate a user’s ability to perform the main activities of the system. Designing an optimized system which may use minimal amounts of resources is not one of the current objectives of the system. These things could both be expanded into and developed, but for now are considered out of scope.

This document will also be reviewed by the teaching assistants and provided peer-review by another design team, creating issues within the GitHub repository to be dealt with accordingly. To ensure feedback is properly actioned, the following process is followed:
\begin{itemize}
    \item Feedback is collected during TA and peer review sessions
    \item Each comment is converted into a GitHub issue
    \item Issues are assigned to a responsible team member
    \item Changes are implemented and committed with reference to the issue
    \item Updated sections are reviewed again before finalizing
\end{itemize}
An issue is considered resolved once the required changes have been implemented, reviewed by at least one additional team member, and the corresponding GitHub issue has been closed. In addition, the test suite derived from this document will be verified via code coverage on the software. For validation, the final outcome of each test will be discussed in the meeting with the project advisor to ensure the system is doing what it should in each test case.

\subsection{Implementation Verification}

The implementation verification plan ensures that the system aligns with the System Requirements Specification (SRS) through both dynamic and non-dynamic testing methodsDynamic testing is conducted through unit testing, integration testing, and system-level validation. Unit tests are implemented for both the frontend and backend components to verify core functionality such as authentication, data handling, and computer vision analysis. Integration testing is used to validate interactions between system components, including Firebase authentication, Firestore database operations, and backend API endpoints such as \texttt{/process\_frame} and \texttt{/precheck\_frame}. Performance testing is also carried out to evaluate response time during exercise recording ($\leq$ 2 seconds), system stability under repeated usage, and handling of real-time data processing. Non-dynamic (static) testing is used to evaluate code and design quality without executing the system. This includes structured peer code reviews on all pull requests to assess correctness, readability, and adherence to best practices. Code walkthroughs are performed for critical modules such as authentication and computer vision analysis to help identify potential issues early. In addition, basic static analysis tools such as \texttt{pylint} are used where applicable to check for common coding issues in the backend. Document reviews are also conducted, with issues tracked and resolved through GitHub. Automated test suites are executed during development to detect regressions and ensure that all existing functionality remains intact. GitHub Actions is used to support automated workflows such as builds and checks on pull requests, helping maintain project stability. Manual testing is also performed for real-time features, including camera-based pose detection and user interaction workflows that cannot be fully automated.

\subsection{Automated Testing and Verification Tools}

\textbf{Unit Testing Framework:}
The project uses standard testing tools for different parts of the system. \texttt{pytest} is used for the Python backend to validate API endpoints, data processing logic, and computer vision functionality. For the frontend, tests are written using \texttt{Jest} to verify UI behavior and component interactions. These tools were selected due to their reliability, documentation support, and compatibility with the development environment.

\textbf{Code Coverage Tools and Plan:}
Code coverage is used to measure how much of the system is exercised by the implemented test cases.

\begin{itemize}
    \item \textbf{Python:} \texttt{pytest-cov} is used alongside \texttt{pytest} to track code coverage for backend components. This includes measuring which parts of the API logic and processing functions are executed during testing.
    
    \item \textbf{TypeScript:} \texttt{Jest} provides built-in coverage reporting for frontend components, tracking execution of functions and user interaction flows.
\end{itemize}

The goal is to achieve meaningful coverage across both codebases, focusing on critical functionality such as authentication, data handling, and core processing logic. Coverage results are used during development to identify untested areas and improve test completeness.

\textbf{Linters and Static Analysis:}
To maintain code quality, basic static analysis tools such as \texttt{pylint} are used for backend code where applicable. In addition, structured peer code reviews and walkthroughs are conducted on pull requests to ensure readability, correctness, and adherence to best practices.

\textbf{Automated Workflows:}
GitHub Actions is used to support automated workflows such as builds and checks on pull requests. While full test automation through CI is not currently implemented, these workflows help ensure that the project remains stable as changes are introduced.

\section{System testing}
This section outlines the tests used to verify both the functional requirements (FRs) and non-functional requirements (NFRs) of the system. Ultimately, these tests ensure that the software behaves as expected in terms of its core functionality, while also meeting performance, usability, and reliability expectations. 

\subsection{Tests for Functional Requirements} 


\begin{enumerate}
	
	\item \textbf{test-TC1 : Physiotherapist Registration (Valid License)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; registration screen accessible; Firebase Auth and Firestore active.
	
	\textbf{Input:} \texttt{registerPhysio()} called with a valid license format and an active license in \texttt{validLicenses}.
	
	\textbf{Output:} Auth user created. Firestore \texttt{users/\{uid\}} written with \texttt{role="physio"}, \texttt{verified=true}, and \texttt{createdAt}. All assertions passed.
	
	\textbf{Test Case Derivation:} Derived from requirement FR1.1 and FR1.2 in the SRS, which state that verified physiotherapists must be able to register successfully using a valid license.

	\textbf{Pass/Fail Criteria:} Pass if the account is created successfully and the correct Firestore fields are written. Fail if registration is rejected or the stored data is incomplete or incorrect.
	
	\textbf{How test will be performed:} Call \texttt{registerPhysio()} with a valid and active license, then verify that authentication succeeds and the correct physiotherapist profile is created in Firestore.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC2 : Physiotherapist Registration (Invalid License Format)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; registration screen accessible.
	
	\textbf{Input:} \texttt{registerPhysio()} called with an invalid license format (missing dash or incorrect digits).
	
	\textbf{Output:} Error ``Invalid license format'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirement FR1.1 and FR1.2 in the SRS, which require that the system validates input format and rejects invalid physiotherapist license formats.
	
	\textbf{Pass/Fail Criteria:} Pass if the invalid license is rejected, the correct error is thrown, and no account data is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPhysio()} with incorrectly formatted license values and verify that registration fails and no user data is written to Firestore.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC3 : Physiotherapist Registration (Unverified License)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; registration screen accessible.
	
	\textbf{Input:} \texttt{registerPhysio()} called with valid format but license not found or \texttt{active=false} in \texttt{validLicenses}.
	
	\textbf{Output:} Error ``License not verified'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirement FR1.1 and FR1.2 in the SRS, which specify that only verified physiotherapists are allowed to create accounts.
	
	\textbf{Pass/Fail Criteria:} Pass if the unverified license is rejected, the correct error is returned, and no account is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPhysio()} with a correctly formatted but unverified license and confirm that the system prevents registration and does not write profile data.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC4 : Patient Registration (Valid Invite Code)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; \texttt{inviteCodes} collection seeded with an active, unused code containing a \texttt{physioId}.
	
	\textbf{Input:} \texttt{registerPatient()} called with a valid invite code.
	
	\textbf{Output:} Auth user created. Firestore \texttt{users/\{uid\}} written with \texttt{role="patient"} and stored \texttt{physioId}. Invite code updated with \texttt{used=true} and \texttt{usedBy=\{uid\}}.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1.1, FR1.3, FR2, and FR3 in the SRS, which state that patients must register using valid invite codes and be linked to a physiotherapist.
	
	\textbf{Pass/Fail Criteria:} Pass if the patient account is created, the linked physiotherapist is stored, and the invite code is marked as used. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPatient()} with a valid invite code and verify account creation, Firestore data, and invite code update behavior.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC5 : Patient Registration (Non-Existent Invite Code)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; \texttt{inviteCodes} collection does not contain the submitted code.
	
	\textbf{Input:} \texttt{registerPatient()} called with a code that does not exist in \texttt{inviteCodes}.
	
	\textbf{Output:} Error ``Invalid invite code'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1.1 and FR1.3 in the SRS, which require that the system rejects invalid or non-existent invite codes during patient registration.
	
	\textbf{Pass/Fail Criteria:} Pass if the invalid code is rejected and no user record is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPatient()} with a code that is not present in the invite code collection and verify that registration is blocked.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC6 : Patient Registration (Inactive Invite Code)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; \texttt{inviteCodes} contains a matching code with \texttt{active=false}.
	
	\textbf{Input:} \texttt{registerPatient()} called with an inactive invite code.
	
	\textbf{Output:} Error ``Invite code inactive'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1.1 and FR1.3 in the SRS, which state that inactive invite codes must not be accepted for patient registration.
	
	\textbf{Pass/Fail Criteria:} Pass if the inactive code is rejected and no account is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPatient()} with an inactive invite code and verify that the request fails and no database writes occur.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC7 : Patient Registration (Already Used Invite Code)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; \texttt{inviteCodes} contains a matching code with \texttt{used=true}.
	
	\textbf{Input:} \texttt{registerPatient()} called with an already used invite code.
	
	\textbf{Output:} Error ``Invite code already used'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1.1 and FR1.3 in the SRS, which enforce that invite codes are single-use and cannot be reused.
	
	\textbf{Pass/Fail Criteria:} Pass if reuse of the invite code is blocked and no new account is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPatient()} using a code already marked as used and verify that the system rejects the request.
	
	
	\vspace{0.5em}
	
	\item \textbf{test-TC8 : Patient Registration (Invite Code Missing Physio Link)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} App launched; \texttt{inviteCodes} contains a matching code with no \texttt{physioId} field.
	
	\textbf{Input:} \texttt{registerPatient()} called with a code missing a \texttt{physioId}.
	
	\textbf{Output:} Error ``Invite code missing physio link'' thrown. No Auth user or Firestore writes created.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1.1, FR1.3, and FR2 in the SRS, which require that patient accounts must be linked to a physiotherapist through a valid invite code.
	
	\textbf{Pass/Fail Criteria:} Pass if the missing link case is rejected and no account data is created. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{registerPatient()} with an invite code that lacks a \texttt{physioId} and verify that the system throws the correct error and rejects registration.

	\item \textbf{test-TC9 : User Login (Valid Physiotherapist Credentials)}
	
	\textbf{Control:} Automated
	
	\textbf{Initial State:} Login screen available; Firestore contains a profile with \texttt{role="physio"}.
	
	\textbf{Input:} \texttt{loginUser()} called with valid PT credentials.
	
	\textbf{Output:} Login returns object with \texttt{uid} and profile data including \texttt{role="physio"}. No errors thrown.
	
	\textbf{Test Case Derivation:} Derived from requirements FR1 and FR1.1 in the SRS, which state that registered physiotherapists must be able to log in using valid credentials.
	
	\textbf{Pass/Fail Criteria:} Pass if login succeeds and the correct physiotherapist profile data is returned. Fail otherwise.
	
	\textbf{How test will be performed:} Call \texttt{loginUser()} with valid physiotherapist credentials and verify that authentication succeeds and the returned user object contains the expected role and profile data.
	
	
	\vspace{0.5em}

	\textbf{Control:} Automated
	
	\textbf{Initial State:} Login screen available; Firestore contains a profile with \texttt{role="patient"}.
	
	\textbf{Input:} \texttt{loginUser()} called with valid patient credentials.

	\textbf{Test Case Derivation:} Derived from requirements FR1 and FR1.1 in the SRS, which state that registered patients must be able to log in using valid credentials.

	\textbf{How test will be performed:} Call \texttt{loginUser()} with valid patient credentials and verify that authentication and profile retrieval both succeed.

	\textbf{Control:} Automated

	\textbf{Input:} \texttt{loginUser()} called with valid credentials.

	\textbf{Test Case Derivation:} Derived from requirements FR1 and FR1.1 in the SRS, which require that login depends on both valid authentication credentials and a valid user profile.

	\textbf{Control:} Automated
	
	\textbf{Initial State:} User session active.

\section{Unit Test Description}

This section outlines the unit testing approach and scope for each of the modules. Please note that the VnV Report contains 
the detailed individual test cases and expected results, but this section essentailly summarizes the plan for the unit testing coverage 
by module as well as the key functionalities that are covered.
\subsection{Authentication}

\subsubsection{Account Creation Module Tests}

\textbf{Goal:} The account creation module verifies that both physiotherapist and patient registration flows behave correctly under valid and invalid conditions. This includes validating physiotherapist license formats, checking license verification status, validating patient invite codes, and ensuring new users are stored correctly in Firebase Authentication and Firestore.

\textbf{Target requirement(s):} FR1.1, FR1.2, FR1.3, FR2, FR3

\begin{itemize}
    \item \textbf{Physiotherapist registration with valid license}
    \begin{itemize}
        \item Ensures a physiotherapist account is created only when the provided license format is valid and verified.
        \item Verifies Firestore user data is written with the correct role, normalized fields, and verification status.
    \end{itemize}

    \item \textbf{Physiotherapist registration failure cases}
    \begin{itemize}
        \item Ensures invalid license formats are rejected with the correct error.
        \item Verifies unverified or inactive licenses do not allow account creation.
    \end{itemize}

    \item \textbf{Patient registration with valid invite code}
    \begin{itemize}
        \item Ensures a patient can register when the invite code is active, unused, and linked to a physiotherapist.
        \item Verifies the patient profile and invite-code usage metadata are stored correctly.
    \end{itemize}

    \item \textbf{Patient registration failure cases}
    \begin{itemize}
        \item Ensures invalid, inactive, already-used, or malformed invite codes are rejected.
        \item Verifies registration does not proceed when a required physiotherapist link is missing.
    \end{itemize}
\end{itemize}


\subsubsection{Valid User Module Tests}

\textbf{Goal:} The valid user module verifies user authentication behavior after account creation. These tests ensure that users with valid credentials can log in successfully, that missing profile information is handled correctly, and that logout functionality clears the active session without error.

\textbf{Target requirement(s):} FR1, FR1.1, SR-AR1

\begin{itemize}
    \item \textbf{Valid login behavior}
    \begin{itemize}
        \item Ensures physiotherapist and patient accounts can log in using valid credentials.
        \item Verifies that profile data is returned correctly after authentication.
    \end{itemize}

    \item \textbf{Login failure handling}
    \begin{itemize}
        \item Ensures login is rejected when the expected Firestore user profile is missing.
        \item Verifies appropriate error handling for incomplete authenticated user states.
    \end{itemize}

    \item \textbf{Logout behavior}
    \begin{itemize}
        \item Ensures an authenticated session can be terminated safely.
        \item Verifies the sign-out operation is called once and completes without error.
    \end{itemize}
\end{itemize}
