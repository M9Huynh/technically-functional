\section{Introduction}
This document presents the results of all tests conducted to evaluate the behaviour and output of 
PhysioCompanion. The report aligns with the test cases outlined in the Verification and Validation (VnV) plan. 
It begins with an evaluation of both functional and non-functional requirements, followed by individual module or
functionality unit tests . The changes implemented after usability testing are then discussed, and the document 
concludes with code coverage statistics and analysis.


\section{Functional Requirements Evaluation}

\begin{enumerate}
	
	\item \textbf{test-TC1 : Physiotherapist Registration (Valid License)}
	
	\textbf{Initial State:} App launched; registration screen accessible; Firebase Auth and Firestore active.
	
	\textbf{Input:} \texttt{registerPhysio()} called with a valid license format and an active license in \texttt{validLicenses}.
	
	\textbf{Output:} Auth user created. Firestore \texttt{users/\{uid\}} written with \texttt{role="physio"}, \texttt{verified=true}, and \texttt{createdAt}. All assertions passed.
	
	\textbf{Result:} Pass
	
	\vspace{0.5em}

\section{Nonfunctional Requirements Evaluation}

\subsection{Usability}

\begin{enumerate}

\item \textbf{UT-1 : Navigation Clarity}

\textbf{Initial State:} App installed on a mobile device; user logged in.

\textbf{Input:} User was asked to find and open the exercise screen, start a recording session, 
and return to the dashboard without assistance.

\textbf{Output:} User successfully navigated through the required screens without confusion. Feedback 
indicated labels and buttons were clear.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{UT-2 : Instruction Clarity During Exercise}

\textbf{Initial State:} User is on the record exercise screen with camera access enabled.

\textbf{Input:} User initiated an exercise session. The application displayed live on-screen feedback 
instructing the user of any adjustments.

\textbf{Output:} User reported that instructions were clear and prompts matched the required actions. 
Minor wording improvements were noted and updated.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{UT-3 : Survey Questionnaire -- ui\_testing}

\textbf{Initial State:} App accessible to testers on mobile devices.

\textbf{Input:} Five users completed a short usability questionnaire addressing ease of use, clarity and navigation.

\textbf{Output:} Average rating across categories was $\geq$ 4/5. Minor UI refinements (font size and button spacing) were applied based on feedback.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-4 : Account Creation (Usability)}
	
\textbf{Initial State:} App installed on participant's device; invite code and PT license number provided.

\textbf{Input:} Participant launched the app, selected their role, and completed account creation.

\textbf{Output:} All participants created accounts successfully without assistance. PT license and invite code fields completed without difficulty. Minor font size feedback noted and resolved.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-5 : Exercise Recording Initiation}

\textbf{Initial State:} Patient logged in on mobile device; camera permission granted; backend server running.

\textbf{Input:} Participant navigated to the Record screen and pressed Start Recording.

\textbf{Output:} Camera activated and pose detection began. On-screen prompts instructed participant to enter the detectable frame area. Navigation and button labels reported as clear.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-6 : Real-Time Pose Detection and Form Feedback}

\textbf{Initial State:} Patient positioned within camera frame; pose detection active; backend returning joint angle and ROM metrics.

\textbf{Input:} Participant performed knee extension repetitions.

\textbf{Output:} App detected relevant body landmarks and displayed appropriate form feedback overlays. Rep count incremented correctly. Detection accuracy was reported as satisfactory.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-7 : Exercise Page (Instructions)}

\textbf{Initial State:} Patient logged in; Exercises tab accessible.

\textbf{Input:} Participant navigated to the Exercises page and reviewed listed exercises.

\textbf{Output:} Exercises displayed with names, target muscle groups, set/rep counts, and step-by-step instructions. Instructions reported as clear and easy to follow.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-8 : Progress Screen (Session History)}

\textbf{Initial State:} Patient logged in with at least one completed session stored in Firestore.

\textbf{Input:} Participant navigated to the Progress tab.

\textbf{Output:} Session history displayed with ROM and rep count data. Layout was readable and logically arranged. Participants suggested adding sets and pain level as future enhancements.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-9 : PT Dashboard (Patient List and Activity)}

\textbf{Initial State:} Physiotherapist logged in; at least one linked patient with recorded sessions.

\textbf{Input:} PT participant reviewed the home dashboard and selected a patient to view their activity history.

\textbf{Output:} Dashboard displayed linked patients and activity history. Patient detail view showed session history and ROM chart. Layout reported as clear and sufficient for clinical use.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{test-UT-10 : PT Feedback Submission}

\textbf{Initial State:} Physiotherapist logged in; patient session detail page accessible.

\textbf{Input:} PT participant selected a session entry and submitted a written comment.

\textbf{Output:} Feedback saved to Firestore and associated with the session. Comment visible from the patient's session view. PT participants rated the feature as clinically useful.

\textbf{Result:} Pass


\end{enumerate}
		
\subsection{Performance}

\begin{enumerate}

\item \textbf{PR-1 : Exercise Interface Response Time -- ex\_int\_speed}

\textbf{Initial State:} User logged in on a mobile device; backend server running.

\textbf{Input:} User started recording from the record screen. Screen recording timestamps were 
used to measure the time from tapping ``Start'' to the first visible feedback/result. There were five trials conducted.

\textbf{Output:} Measured response times were 1.87s, 1.92s, 1.79s, 1.95s, and 1.84s. The average end-to-end 
response time was 1.87 seconds ($\leq$ 2 seconds).

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{PR-2 : Repeated Use Performance}

\textbf{Initial State:} Application running normally on mobile device.

\textbf{Input:} User completed 10 consecutive ``Start $\rightarrow$ Record Exercise $\rightarrow$ Stop'' cycles.

\textbf{Output:} There was no significant slowdown observed across the 10 trials. Additionally, the response times were all within acceptable 
range and no crashes took place.

\textbf{Result:} Pass

\end{enumerate}

\subsection{Reliability and Fault-Tolerance}

\begin{enumerate}

\item \textbf{RFT-1 : Backend Failure Handling -- fail\_recovery}

\textbf{Initial State:} User actively using the application while connected to backend.

\textbf{Input:} Backend server was manually terminated during active analysis.

\textbf{Output:} Application displayed a network error message and remained responsive (no crash). After backend 
restart, the user was able to retry and continue normal operation.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{RFT-2 : Network Interruption During Upload -- Interrupted\_vid}

\textbf{Initial State:} User uploading recorded exercise video.

\textbf{Input:} WiFi connection was disabled mid-upload and restored after approximately 10 seconds.

\textbf{Output:} Application detected upload failure and displayed a retry option. User retried successfully and 
uploaded video was verified to be intact.

\textbf{Result:} Pass

\end{enumerate}

\begin{enumerate}

\textbf{Output:} Server returned HTTP 401 Unauthorized. Additionally, no protected data was returned.

\textbf{Result:} Pass

\vspace{0.5em}

\item \textbf{SR-2 : Invalid Credentials Login}

\textbf{Initial State:} Application login screen available.

\textbf{Input:} Login attempted using an email not registered in the database or incorrect password.

\textbf{Output:} System denied login and displayed an appropriate error message without exposing any 
system details.

\textbf{Result:} Pass

\vspace{0.5em}


\end{enumerate}

issues were documented and resolved.

\textbf{Output:} The core functions passed unit testing. The UI refinements were implemented based on peer 
feedback. The code structure maintained clear separation between modules and frontend components. Overall, there 
were no major functional issues identified during review.

\textbf{Result:} Pass

\section{Changes Due to Testing}

\subsection{Usability Testing Results}
Analyses from usability testing revealed important user experience insights which has provided clarity with what should
be the focus for further development. A subset of recommendations will be developed further, while others will be tabled 
as out of scope due to project timeline constraints. 
There were a total of 5 participants in the study, with 2 being PTs, and the rest were those who satisfied the pool criteria.
The diverse perspectives proved to be essential by honing in on elements that may provide substantial added value to the 
application. Both user flows (PT and patient) were tested with the corresponding participants. \\
The physiotherapist participants had 2 recommendations: A more comprehensive exercise activity record (eg. adding sets in addition to reps) 
for a clearer picture on the patient's performance, and inclusion of a post-exercise feedback form to provide an insight into performance.
(eg. modifying the rep count due to patient's increased pain). \\
The other participants highlighted the need for audio cues while performing the exercise. Reading the instructions from
the acceptable distance necessary for proper application function was troublesome. Secondly, additional data on the Progress tab would
be beneficial for patients to keep track, in a non-technical context, of their recovery. \\
Please refer to the \href{../Extras/UsabilityTesting/UsabilityReport.pdf}{Usability Report} for additional information.\\

\section{Automated Testing}

In terms of automated testing, all of the tests for the TypeScript frontend modules as well as the Python backend 
are automated. When it comes to running the tests, the Python tests are run using \texttt{Pytest} by simply typing \texttt{pytest} in the command line in the correct 
root project directory. These tests validate core backend functionality such as the metric calculations and helper 
functions utilized during exercise processing. Additionally, all of the TypeScript tests can be run in the same manner, however, they run 
with \texttt{Jest} and through running the following command: \texttt{npm run test} instead. Ultimately, these tests focus on validating frontend logic including authentication and user account
 management, user activity tracking, exercise data handling, performance statistics generation, and the feedback 
 module that displays live feedback to users and allows both the physiotherapistss and patients the opportunity 
 to leave comments regarding the user's respective session. It is important to note that the both the Firebase calls and 
 camera components are mocked during testing so that we are able to separately test the logic functionality. 
 Also, the output results for both the frontend and backend automated test suites are printed to the console, ultimately 
 allowing us to be able to quickly identify both the passing and failing tests immediately.

\section{Extras}

The extras set out for the system consist of both a Design Thinking Document and a Usability Report. The Design Thinking Document aims to explain the process behind, and work done towards, the final design of the system. This document explains the overall flow of processing through the system and the interfacing elements, external libraries utilized, and more.     Our project currently uses GitHub Actions for CI, but as of right now, the workflow is limited and 
    mainly displays the pull request activity and build checks. With our implemented unit tests for both 
    the frontend and backend, we want to integrate these directly into the CI pipeline. Specifically, the 
    GitHub Actions workflow could be configured to automatically run the Jest test suite for the TypeScript 
    frontend and the Pytest test suite for the Python backend whenever a pull request is opened or updated.
